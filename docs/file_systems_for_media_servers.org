#+title: File systems for media servers

This file documents considerations relevant to file systems in a media server context.

* Media server solution: SnapRAID and MergerFS

The ideal:
1. No large upfront cost in drives
2. Mismatched drive sizes
3. Expandable array size, without reformatting drives
4. High usable space relative to total drive space
5. FOSS (no subscriptions or licenses)
6. Resilient against a few drive failures
The combination of *SnapRAID with MergerFS* is perfect for the above requirements. MergerFS gives storage flexibility (1, 2, 3) while SnapRAID gives redundancy (2,[fn:1] 3, 4, 6). The following solutions are inadequate:
+ ZFS (fails 1, 2, 3)
+ RAID (fails 4)
+ unRAID (fails 5)
See also [[https://perfectmediaserver.com/02-tech-stack/mergerfs/][mergerfs - Perfect Media Server]] for another person's justification of this decision in the same context.

There are a few downsides of SnapRAID with MergerFS in comparison to the alternatives that I am comfortable with given my use case (media server):
+ SnapRAID parity is not real-time; it uses snapshots (~snapraid sync~), hence the name. This is fine with a media server where data is almost always static.
  - If one needs a real-time solution, use e.g. a ZFS RAID array or unRAID.

** Torrenting

A torrenting-specific detail: torrenting large binary files creates high degrees of fragmentation, since each piece of the file is written randomly to a location on disk with COW (which matters for HDDs). As such, to greatly reduce disk fragmentation, incomplete torrent files should be NOCOW (the complete torrent files are fine to be COW, since they will be written in sequential chunks). However, the NOCOW file attribute is retained on moves[fn:2]---unless the move is to a separate subvolume, which makes the move essentially a copy[fn:3]. So in total, *one should have their incomplete downloads directory a separate NOCOW subvolume.*[fn:4]

2026-01-15:
Although [[https://www.reddit.com/r/qBittorrent/comments/1ecdmfg/comment/lezmjyj/?utm_source=share&utm_medium=web3x&utm_name=web3xcss&utm_term=1&utm_content=share_button][this comment]] suggests that fragmentation doesn't matter when seeding many torrents since in such a case random IO occurs anyway...

I think the idea is this: if the file is complete, readahead makes it such that there are always reads queued as the drive seeks. So the seeking time isn't the bottleneck, the predictability of the reads (i.e., the "access pattern") is. Consequently, fragmentation doesn't affect the speed of reads and writes /for sequential reads (e.g., single file), as opposed to random (e.g., jumping between many files) reads/: seek speed is increased but is masked by the kernel's readahead.

[fn:2] I learned about this from [[https://www.reddit.com/r/btrfs/comments/s7qz6d/torrenting_on_btrfs_fragmentation_and_drive/][several comments from this Reddit thread]].

[fn:3] In this context, the trade off of a single copy of a large file is much smaller than the HDD seeking speed degradation we're trying to avoid (for large torrented binary files) due to high fragmentation.

[fn:4] Additionally, since the first mounted subvolume's options are applied to all mounted subvolumes (see [[https://man.archlinux.org/man/btrfs.5#MOUNT_OPTIONS][btrfs(5) — Arch manual pages]]), one must use ~chattr +C /path/to/incomplete/downloads~ to make the specific directory NOCOW rather than the entire subvolume. (And to repeat, a separate subvolume is needed to exploit the trick of turning a NOCOW file into a COW one when moved into a COW subvolume.)
